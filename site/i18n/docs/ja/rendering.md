# レンダリングの仕組み

## ループ

どのバインディングも同じループを実行します。

```rust,ignore
if chart.needs_redraw() != Invalidation::None {
    chart.build_frame(now_ms, &renderer.measurer()); // &mut chart, ends here
    renderer.render(chart.frame(), &chart.data_view())?; // two shared borrows
}
```

何も変わらない間`needs_redraw`は`None`のままなので、アイドル状態のチャートにはコストがかかりません。フレームの構築にかかる時間は約20 µsで、データのサイズには依存しません。

## フレーム

`Frame`には3つのレイヤーがあります。背景（グリッド）、メイン（シリーズ、軸）、オーバーレイ（クロスヘア）で、それぞれがリビジョン番号付きの描画コマンドのフラットなリストです。シリーズは矩形に展開されません。フレームは「このシリーズを、表示範囲i..jで、この変換を使って描画せよ」と指示し、レンダラーはデータのカラムを直接読みます。

クロスヘアだけが動いた場合はオーバーレイのリビジョンだけが変わり、GPUレンダラーは他の2つのレイヤーのキャッシュ済みテクスチャを再利用します。

## GPU上のデータ

wgpuレンダラーは、シリーズのデータを4096本単位のチャンクでGPUバッファに保持します。チャンクは初めて描画されるときにアップロードされ、その後は変更された範囲だけがアップロードされます。パンとズームではチャンクごとにいくつかの数値が変わるだけで、再アップロードは発生しません。

価格はチャンクごとの基準価格からの相対値で保存されるため、価格が大きくティックが小さい場合でも、GPU上の32ビット浮動小数点数で完全な精度が保たれます。

## どこでも同じピクセル

座標の計算は`ferrochart_core::transform_helpers`にあり、WGSLシェーダーでも演算単位で同じ処理を再現しているため、CPUとGPUのレンダラーは同じように丸めます。黄金画像テストでは、両方を同じ参照画像と比較します。（注意点が1つあります。GPUコンパイラーは`a * b + c`を丸め方の異なる単一の命令に融合することがあるため、変換は融合できない`(a + b) * c`の形で書かれています。）
